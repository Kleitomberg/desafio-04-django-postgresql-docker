1. Imagem × Container

O Dockerfile é a receita; docker build gera a imagem (imutável). docker run cria um container a partir dela. O hostname acima é o ID do container — recrie o container e ele muda.

2. Rede: por que DB_HOST=postgres-desafio4?

Dentro de uma docker network customizada, o Docker resolve o nome do container como DNS. Por isso o Django acha o banco pelo nome, e não por localhost (que dentro do container aponta para ele mesmo).

docker network create desafio4_net
docker run -d --name postgres-desafio4 --network desafio4_net \
  -e POSTGRES_DB=desafio4_db -e POSTGRES_USER=admin -e POSTGRES_PASSWORD=... \
  -v desafio4-pgdata:/var/lib/postgresql/data postgres
docker run -d --network desafio4_net -p 8007:8000 --env-file .env desafio4-django

3. Volume: persistência

O sistema de arquivos do container some com ele. O volume desafio4-pgdata guarda /var/lib/postgresql/data fora do container: você pode apagar e recriar o Postgres e seus dados (inclusive o superuser) continuam lá.

4. Variáveis de ambiente

O .env não vai para a imagem (está no .dockerignore); ele é injetado em tempo de execução com --env-file. O settings.py lê tudo com os.environ. Assim a mesma imagem roda em qualquer ambiente.

5. Arquivos estáticos (o bug do admin)

Com DEBUG=0 o Django não serve /static/, e o Gunicorn também não. O collectstatic (rodado no build) reúne os arquivos em STATIC_ROOT, e o WhiteNoise no MIDDLEWARE os serve. Esta página está estilizada inline justamente para não depender disso; o admin depende.
